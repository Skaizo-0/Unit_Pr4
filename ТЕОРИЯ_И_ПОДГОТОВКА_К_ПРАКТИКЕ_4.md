## ЧАСТЬ 1. ВСЯ НЕОБХОДИМАЯ ТЕОРИЯ (ПРОСТЫМИ СЛОВАМИ)

### 1.1. Бюджет кадра (Frame Budget) и частота кадров (FPS)
Компьютерная игра — это непрерывная смена кадров:
- Чтобы игра шла плавно при **60 FPS** (кадрах в секунду), на отрисовку одного кадра есть всего **16.6 миллисекунд** ($1000 \text{ мс} / 60$).
- При **30 FPS** бюджет кадра составляет **33.3 миллисекунды**.

За эти считанные миллисекунды процессор (CPU) должен успеть:
1. Обработать физику (PhysX).
2. Выполнить логику всех скриптов (C# код, `Update()`).
3. Рассчитать анимации, звук, искусственный интеллект.
4. Подготовить команды отрисовки для видеокарты (Draw Calls / Render Thread).

Если только **один скрипт** забирает себе **1.1 – 1.5 мс** на каждом кадре на какую-то простую операцию, он «съедает» почти 10% всего бюджета 60 FPS. Если таких участков несколько, игра неизбежно начинает фризить и лагать.

---

### 1.2. Вычислительная сложность алгоритмов (Big-O нотация)
Сложность показывает, как возрастает время работы алгоритма при росте количества данных ($N$).

1. **$O(1)$ — Константная сложность (мгновенно):**
   - Время операции не зависит от количества элементов. Будь в базе 10 записей или 10 000 000 — поиск займет одинаковое микроскопическое время.
   - **Пример:** Взять книгу из шкафа, если мы заранее знаем точный номер полки; получение элемента из **хэш-таблицы (Dictionary)** по ключу.

2. **$O(N)$ — Линейная сложность:**
   - Время растет прямо пропорционально числу элементов $N$. Чтобы найти нужный элемент, приходится перебирать массив с самого начала и сравнивать каждый элемент.
   - **Пример:** В шкафу 4096 книг лежат в случайном порядке, и мы ищем нужную, перебирая каждую по очереди.

3. **$O(N \times Q)$ — Квадратичная/пакетная сложность (БОТЛНЕК):**
   - У нас есть база из $N$ элементов (в нашей практике $N = 4096$) и пачка из $Q$ запросов (в практике $Q = 1024$).
   - Если для каждого из 1024 запросов мы запускаем полный перебор массива из 4096 элементов:
     $$\text{Количество операций в худшем/среднем случае} \approx N \times Q = 4096 \times 1024 = 4\,194\,304 \text{ итераций!}$$
   - И всё это крутится **в каждом кадре** игрового цикла! Именно это и вызывало просадку CPU.

---

### 1.3. Массив против Хэш-таблицы (Dictionary)
- **Обычный массив (`Record[]`):**
  - Элементы лежат подряд в памяти.
  - Если мы знаем точный индекс (например, `records[5]`), доступ мгновенный.
  - Но если мы ищем запись по идентификатору `Id`, который не равен номеру ячейки, приходится бежать циклом `for` и проверять `if (records[i].Id == query)`. Это долго ($O(N)$).
- **Хэш-таблица (`Dictionary<int, int>` в C#):**
  - При добавлении пары «ключ-значение» ключ пропускается через математическую хэш-функцию, вычисляющую номер внутренней корзины (bucket).
  - При поиске `index[key]` процессор сразу вычисляет ячейку и мгновенно достает значение за $O(1)$.

### 1.4. Профилирование в Unity (Unity Profiler)
**Unity Profiler** — встроенный инструмент анализа производительности игры:
- **Main Thread (Главный поток):** Поток, где крутится весь игровой движок и выполняются методы Unity (`Update`, `FixedUpdate`, события ввода и рендера).
- **ProfilerMarker:** Именованная метка в коде C# (в нашей работе: `Lesson4.LookupBatch`). Позволяет профилировщику изолированно замерять время выполнения конкретного блока кода.
- **Hierarchy View (Иерархия):** Режим отображения, в котором дерево вызовов разложено по полочкам:
  - `Time ms` — сколько миллисекунд выполнялся блок в выбранном кадре.
  - `Calls` — сколько раз был вызван метод за данный кадр (в нашей практике строго 1 раз).
  - `GC Alloc` — сколько байт мусора выделил метод в управляемой куче (garbage collector). У нас 0 B (аллокаций памяти нет).
- **Deep Profile (Глубокое профилирование):** Режим, принудительно замеряющий абсолютно каждый метод C#. Для замеров его отключают, так как он сам по себе сильно замедляет программу и искажает замеры.

---

### 1.5. Почему статистика измеряется медианой, а не средним арифметическим?
В бенчмарках операционная система Windows постоянно выполняет фоновые задачи (обновления, антивирус, прерывания железа, планировщик потоков).
- Если из 300 кадров 299 кадров шли по 0.01 мс, а на одном кадре антивирус вызвал скачок на 15 мс:
  - **Среднее арифметическое** подскочит и покажет искаженную картину (~0.06 мс).
  - **Медиана (Median)** — это значение ровно в середине отсортированного списка замеров. Она полностью игнорирует случайные внешние выбросы и показывает реальную чистую производительность кода.
- **IQR (Interquartile Range — межквартильный размах):** Разница между 75-м и 25-м процентилями. Показывает стабильность и разброс времени кадра.

### 1.6. Поиск регрессий через Git Bisect
Когда над проектом работают десятки разработчиков и делают сотни коммитов, в какой-то момент игра начинает тормозить (появляется регрессия).
- Перебирать вручную все 50-100 коммитов подряд — колоссальная потеря времени.
- **`git bisect`** использует алгоритм **бинарного поиска (деление пополам, $O(\log N)$)**:
  1. Указываем заведомо рабочий старый коммит (`good`) и плохой свежий коммит (`bad`).
  2. Git переключает репозиторий ровно посередине между ними.
  3. Мы запускаем тест. Если в этой точке всё хорошо — говорим `git bisect good`. Если уже тормозит — говорим `git bisect bad`.
  4. Область поиска каждый раз сокращается в 2 раза. Всего за 3–4 шага среди десятков коммитов находится точный коммит, сломавший производительность.

## ЧАСТЬ 2. ПРАКТИКА 4.1: ОПТИМИЗАЦИЯ КРИТИЧЕСКОГО УЧАСТКА КОДА

### 2.1. Исходная ситуация
В проекте `unity-cpu-practice` симулируется типичная игровая задача: сервер или система игры присылает пачку из 1024 запросов идентификаторов (`queries`), и для каждого нужно вернуть связанное числовое значение.

### 2.2. Разбор кода `LookupExercise.cs`

#### Исходный код (ДО оптимизации):
```csharp
public int ExecuteBatch(int[] queries, int[] results)
{
    int checksum = 0;
    // Цикл 1: Проходимся по каждому из 1024 запросов
    for (int query = 0; query < queries.Length; query++)
    {
        int value = -1;
        // Цикл 2 (УЗКОЕ МЕСТО!): Для каждого запроса в лоб перебираем все 4096 записей массива
        for (int item = 0; item < records.Length; item++)
        {
            if (records[item].Id == queries[query])
            {
                value = records[item].Value;
                break;
            }
        }
        results[query] = value;
        checksum += value;
    }
    return checksum;
}
```
**В чём была беда:**  
Массив `records` содержит 4096 записей. Чтобы найти значение для одного запроса, цикл крутится сотни и тысячи раз. Для 1024 запросов суммарное число итераций приближалось к двум миллионам. Это отнимало **~1.10 миллисекунды** на кадре.

#### Исправленный код (ПОСЛЕ оптимизации):
```csharp
public int ExecuteBatch(int[] queries, int[] results)
{
    int checksum = 0;
    // Проходимся по 1024 запросам
    for (int query = 0; query < queries.Length; query++)
    {
        // Мгновенное получение значения из готовой хэш-таблицы за O(1)
        int value = index[queries[query]];
        results[query] = value;
        checksum += value;
    }
    return checksum;
}
```
**Почему это сработало:**  
Словарь `Dictionary<int, int> index` уже был заботливо создан и заполнен в методе `Awake()` при запуске игры:
```csharp
index.Add(id, value);
```
Нам оставалось лишь перестать перебирать массив и обратиться к словарю по ключу `queries[query]`. Время поиска одного элемента упало с микросекунд до наносекунд.

## ЧАСТЬ 3. ПРАКТИКА 4.2: ПОИСК РЕГРЕССИИ ЧЕРЕЗ GIT BISECT

### 3.1. Суть задания
В учебном репозитории с историей разработки (переданном в архиве `history.bundle`) кто-то из разработчиков случайно или намеренно испортил алгоритм, и производительность упала в сотни раз.
Задача: используя автоматический инструмент `git bisect` и тестовый C#-скрипт проверки, найти точный хэш коммита-виновника, его автора, дату и причину регрессии.

---

### 3.2. Как работал тестовый скрипт `Проверить.ps1`
Скрипт запускает Unity в фоновом консольном режиме (`batchmode -nographics`) и выполняет специальный тестовый метод `HistoryRegressionCheck.Run()`:
- Тест выполняет инициализацию и пачку запросов.
- Специальный счётчик обращений `LookupAccessCounter` считает **каждое обращение к памяти данных (inspections)**.
- Установлен лимит: **бюджет $\le 8192$ обращений**.
- Если обращений $\le 8192$, тест завершается с кодом **0 (good)**.
- Если обращений больше 8192, тест падает с кодом **1 (bad)**.

---

### 3.3. Пошаговый процесс поиска через Git Bisect
Вся история содержала диапазон между заведомо хорошим коммитом `known-good` (`2311165`) и испорченным коммитом `reported-bad` (`433b388`).

1. **Старт поиска:**
   ```bash
   git bisect start reported-bad known-good
   ```
   Git сообщил: осталось протестировать 3 ревизии (~2 шага).

2. **Шаг 1: Проверка коммита `c199b8d` ("Document supported identifier range"):**
   - Запустили проверку: `inspections = 5120`, budget = 8192.
   - Число обращений в норме!
   - Команда: `git bisect good`.

3. **Шаг 2: Проверка коммита `844c635` ("Label the lookup exercise"):**
   - Запустили проверку: `inspections = 2059776` (в 251 раз выше нормы!).
   - Команда: `git bisect bad`.

4. **Шаг 3: Проверка коммита `8ebb0ea` ("Use records directly in query resolution"):**
   - Запустили проверку: `inspections = 2059776` (бюджет превышен!).
   - Команда: `git bisect bad`.

5. **Финальный вердикт Git:**
   ```text

   Author: CPU Practice <cpu-practice@example.invalid>

   ```

### 3.4. Анализ дифа (что сломал плохой коммит)
Команда `git show 8ebb0ea` наглядно показала преступление разработчика:
```diff
--- a/Assets/Scripts/LookupExercise.cs
+++ b/Assets/Scripts/LookupExercise.cs
@@ -49,9 +49,15 @@ public sealed class LookupExercise : MonoBehaviour
         for (int query = 0; query < queries.Length; query++)
         {
-            int value;
-            if (!index.TryGetValue(queries[query], out value))
-                value = -1;
+            int value = -1;
+            for (int item = 0; item < records.Length; item++)
+            {
+                if (records[item].Id == queries[query])
+                {
+                    value = records[item].Value;
+                    break;
+                }
+            }
```
Разработчик удалил быстрый поиск по словарю `index.TryGetValue` и вернул медленный цикл `for` по массиву `records`! Из-за этого количество чтений подскочило с 5 120 до 2 059 776.

## ЧАСТЬ 4. ШПАРГАЛКА ДЛЯ ЗАЩИТЫ (ВОПРОСЫ И ОТВЕТЫ ПРЕПОДАВАТЕЛЮ)

**В: Какая была сложность алгоритма до и после оптимизации в 4.1?**  
**О:** До оптимизации была квадратичная сложность $O(N \times Q)$, где $N = 4096$ записей, а $Q = 1024$ запросов. После оптимизации сложность стала линейной относительно числа запросов $O(Q)$, так как каждый отдельный запрос к хэш-таблице выполняется за $O(1)$.

**В: Почему нельзя было просто взять среднее арифметическое времени кадра? Зачем медиана?**  
**О:** Среднее арифметическое чувствительно к случайным системным выбросам (работа антивируса, переключение потоков ОС, сборка мусора). Медиана берет значение строго по центру отсортированного ряда и отсекает аномальные пики, давая объективную оценку производительности кода.

**В: Как вы гарантировали, что оптимизированный код не стал выдавать мусорные данные?**  
**О:** Мы сверяли контрольную сумму (`checksum = 6168064`) и флаг поэлементной валидации (`valid: True`). Для всех 1024 запросов на протяжении 300 измерительных кадров результаты полностью совпали с эталонными.

**В: Что такое маркер `Lesson4.LookupBatch` в профайлере?**  
**О:** Это экземпляр `ProfilerMarker`, объявленный в коде бенчмарка. Конструкция `using (BatchMarker.Auto())` позволяет профилировщику Unity точно замерить блок выполнения метода `ExecuteBatch` в главном потоке без необходимости включать тяжелый режим Deep Profile.

**В: В чём суть коммита-виновника в Практике 4.2?**  
**О:** Первый плохой коммит `8ebb0ea` ("Use records directly in query resolution"). В нём разработчик заменил эффективный поиск по хэш-индексу `index.TryGetValue` на линейный перебор массива `records`, что вызвало рост обращений к данным с 5 120 до 2 059 776 при лимите в 8 192.
